# 周边去哪儿（nearby-explorer）

## 何时使用

用户给了一个**起点**（经纬度、地名或地铁站名）和一句**自然语言需求**（如"想找家咖啡馆、步行 15 分钟内、最多 3 家、优先近的"），
需要附近地点推荐，并要知道**走过去要多久**。

## 输入

| 槽位 | 从需求中抽取 | 缺省值 |
| --- | --- | --- |
| 城市 `city` | 需求里出现的城市名 | 由起点坐标逆地理编码得到；再不行用 `maps_ip_location` |
| 起点 `origin` | 明确给出的经纬度，或可定位的地名/地铁站 | 评测会给出坐标；若只给地名则按 `maps_geo` 解析 |
| 地点类型 `keywords` | 咖啡馆 / 餐厅 / 公园 / 便利店 … | 缺失时按「附近值得去的地点」处理，并在回答里说明这一假设 |
| 步行上限 `max_walk_min` | "步行不超过 15 分钟" → 15 | 20 |
| 推荐数量 `top_n` | "最多 3 家" → 3 | 3（**上限 3**） |
| 排序偏好 `sort_by` | "优先近一点" → 时间/距离升序；"评分高" → 评分降序 | 时间升序 |

> **这是单轮任务：不要向用户反问。** 任何槽位缺失都按上表缺省值继续执行，
> 并在回答里用一句话说明你假设了什么（例如"未指定类型，按『附近值得去的地点』处理"）。
> 反问会导致本轮没有可用回答。

抽取后**先用一句话复述条件**（例如"起点 X，找咖啡馆，步行 ≤15 分钟，最多 3 家，按时间从近到远"），再开始查询。

## 工具与字段映射

| 用途 | 高德 MCP 工具（名称可能略有差异，按能力匹配同类工具） | 取什么字段 |
| --- | --- | --- |
| 起点归一化（地名 → 坐标） | `maps_geo`（地理编码） | `location` |
| 起点归一化（站名 / 模糊名 → POI） | `maps_text_search` | 候选 POI 的 `location` |
| 周边搜索 | `maps_around_search` | `pois[]` 的 `name` / `address` / `location` / `type` / `rating`（若有） |
| 步行路线 | `maps_direction_walking` | `paths[0].distance`（米）、`paths[0].duration`（秒） |
| （可选）POI 详情 | `maps_search_detail` | 营业时间、评分等（仅在确有返回时使用） |

**坐标格式**：高德使用「经度,纬度」，形如 `120.163,30.274`，小数不超过 6 位。

> **工具名兼容**：不同接入方式暴露的名称可能略有差异。若运行时没有上表中的精确名字，
> 按能力挑选最接近的同族工具再调用（例如周边搜索也可能叫 `maps_search_around`、
> 步行规划也可能叫 `maps_direction_walk`）。**先看当前会话真正暴露了哪些工具，再决定调哪个**，
> 不要凭记忆硬编一个不存在的方法名。

## 执行流程（按序，不得跳步）

### 步骤 0：归一化起点

1. 需求已给经纬度 → 直接使用，跳到步骤 1。
2. 给的是地名/地址 → `maps_geo(address=地名, city=city)` 取 `location`。
3. 给的是地铁站/商场等 POI 名 → `maps_text_search(city=city, keywords=名称)`，取**第一条**结果的 `location`；若返回多条同名，优先 `type` 含"地铁站/购物中心"的那条，并在回答里注明用的是哪个（如"XX 地铁站 C 口"）。
4. 三种方式都失败 → 说明"无法确定起点位置"，请用户给经纬度或更具体的地址；**不得**用城市中心点代替。

### 步骤 1：周边搜索

1. 初始半径 `R = clamp(max_walk_min × 80, 500, 5000)` 米（步行约 80 米/分钟）。
2. 调 `maps_around_search(location=origin, keywords=类型词, radius=R)`。
   该工具契约只有这三个参数（`location` 必填、`keywords` 类型词、`radius` 单位米且上限 50000），
   **不要传 `page` / `offset` 等未声明的参数**——多传参数可能导致整次调用报错，直接影响推荐结果。
3. 候选不足 `2 × top_n` 条时，把 `R` 放大到 `min(R × 1.5, 5000)` 重查一次；**最多两轮**，避免无意义调用。
4. 记录每条 POI 的 `id`/`name`/`address`/`location`/`type`，后续所有输出只能引用这些字段。

### 步骤 2：逐个查步行路线（**不可省略、不可用直线距离代替**）

对候选 POI（建议取前 8 条，按 `location` 去重，同一连锁店不同门店算不同 POI），逐个调用：

```
maps_direction_walking(origin=起点坐标, destination=该 POI 的 location)
```

取 `paths[0].distance`（米）与 `paths[0].duration`（秒）。若该 POI 无步行路线（返回空 paths），
记为"无步行路线"并排除，不能补一个估算值。

### 步骤 3：硬性过滤

按顺序筛掉：

1. `duration > max_walk_min × 60` 的（**超时的一律不作为符合条件的推荐**）；
2. 名称/类型与需求明显不符的（要咖啡馆却返回五金店、要求"公园"却返回停车场）；
3. 无坐标或无步行路线的。

### 步骤 4：排序与截断

- 默认：`duration` 升序（时间相同则 `distance` 升序）。
- 用户说"评分高/环境好"且工具返回了 `rating`：先 `rating` 降序，同分再按 `duration` 升序；**没有 rating 就不要假装按评分排序**。
- 取前 `min(top_n, 3)` 条。

### 步骤 5：组织回答（见下节模板）

## 输出格式

```
按你说的条件（起点：<起点名称>，<类型>，步行 ≤ <N> 分钟，最多 <M> 家，<排序口径>），
我在 <R> 米范围内查到 <K> 个候选，其中有 <P> 个步行时间符合要求：

| # | 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|------|------|---------:|---------:|----------|
| 1 | <name> | <address> | <distance> 米 | <duration> 分钟 | <理由> |
| 2 | … | … | … | … | … |

说明：<筛选过程 / 未推荐的原因 / 未核实的信息>
```

规则：

- **距离**：`< 1000` 米用「米」，`≥ 1000` 米用「公里」且保留 1 位小数（如 `1.2 公里`）。
- **时间**：`duration / 60` 四舍五入到整数分钟；可附「约」字。
- **推荐理由**：只能引用工具返回的事实，例如
  「步行 6 分钟，是候选中最近的」「评分 4.6，候选中最高（高德返回）」「类型为『咖啡馆』，符合需求」。
  **不得**写「很安静」「不排队」「人少」「环境好」这类无数据支撑的描述——这类信息一律标「未核实」。
- 数量不足 `top_n` 时，如实给出实际数量，例如「只找到 2 个符合条件的，其余候选步行都超过 15 分钟」。

## 边界处理（这几种情况必须如实说明）

| 情况 | 必须怎么答 |
| --- | --- |
| 0 个符合条件 | 说明「在 <R> 米 / 步行 <N> 分钟内没有找到符合条件的 <类型>」，并给 3 个放宽建议：扩大半径、换类型词、放宽时间 |
| 候选够但多数超时 | 列出符合条件的少量地点，并说明「另有 X 个步行超过 N 分钟，未列入」 |
| 工具报错/超时 | 重试 1 次（换关键词或缩小半径）；仍失败则明确「高德查询失败（错误信息）」，**不编造地点或路线** |
| 请求超出能力 | 如要求驾车/公交/多站行程，说明本 Skill 只做「起点 → 单个地点」的步行方案；需要的话可再单独查询 |
| 营业状态/排队/人均 | 工具未返回就写「未核实」，不得推测 |

## 禁止事项

1. 不得用直线距离、坐标差或"大概 X 米"代替步行路线查询结果；
2. 不得编造 POI 名称、地址、坐标、距离、时间；
3. 不得把多个地点串成一条行程（各地点都是从同一起点出发的**独立备选**）；
4. 不得把工具未返回的属性当作事实写入推荐理由；
5. 不得为了凑满 3 条而放宽用户明确给出的硬条件（步行上限）。

## 示例（数值均来自工具返回，此处用占位符表示）

> 输入：我在杭州西湖文化广场地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。

执行要点：
1. `maps_text_search(city=杭州, keywords=西湖文化广场地铁站)` → 起点坐标 `<origin>`
2. `maps_around_search(location=<origin>, keywords=咖啡馆, radius=1200)` → 候选 `<POI-A/B/C/D…>`
3. 对每个候选 `maps_direction_walking(origin=<origin>, destination=<POI 坐标>)` → 各自的 `distance`/`duration`
4. 过滤掉 `duration > 900s` 的，按 `duration` 升序取前 3
5. 输出：

```
按你说的条件（起点：西湖文化广场地铁站，咖啡馆，步行 ≤ 15 分钟，最多 3 家，按时间从近到远），
我在 1200 米范围内查到 9 个候选，其中有 4 个步行时间符合要求：

| # | 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|------|------|---------:|---------:|----------|
| 1 | <POI-A name> | <POI-A address> | 420 米 | 6 分钟 | 候选中步行时间最短 |
| 2 | <POI-B name> | <POI-B address> | 650 米 | 9 分钟 | 步行 9 分钟，评分 <rating>（高德返回） |
| 3 | <POI-C name> | <POI-C address> | 880 米 | 12 分钟 | 步行 12 分钟，在 15 分钟限制内 |

说明：另有 5 个候选步行超过 15 分钟，未列入；营业状态与排队情况未核实。
```

## 交付前自查（5 条全过再输出）

- [ ] 每个地点的名称/地址都来自 `maps_around_search` 的返回字段，没有自行补全
- [ ] 每个步行距离/时间都来自 `maps_direction_walking`，没有用直线距离推算
- [ ] 没有超时地点混进"符合条件的推荐"
- [ ] 推荐理由里没有无数据支撑的主观描述（安静/排队/人多）
- [ ] 结果不足或查询失败时，说明原因并给了放宽建议
