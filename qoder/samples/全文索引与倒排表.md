# 全文索引与倒排表

## 1. 为什么需要倒排表

顺序扫描要对每个文档逐字读取，判断查询词是否出现，时间复杂度与语料总量成正比。倒排表把「文档 → 内容」的顺序反过来：它为每个词项建立一条 posting list，记录该词项出现在哪些文档、出现多少次、在文档中的位置。查询时只访问包含查询词项的 posting list，再求交集或并集，因此能跳过绝大多数无关文档。词项的文档频率（DF）就是 posting list 的长度，它既用于估算检索代价，也是 BM25 计算 IDF 权重的输入。文档频率越低的词项区分度越高，查询优化器通常先处理 DF 小的词项。

## 2. 倒排表的组织方式

词项词典保存词项到 posting list 的映射，常见实现是哈希表加有序数组，或者像 Lucene 那样使用 FST。posting list 内部按文档编号升序排列，便于做跳跃（skip）与交集。为了节省空间，文档编号常用差分编码，位置信息则单独存放，只有短语查询才需要读取。压缩算法如 PForDelta、Roaring Bitmap 能在保持随机访问能力的同时显著降低存储。倒排表的更新代价较高，因此工业系统通常采用分段写入，后台再合并段文件；这与 LSM 的思路相似，但搜索引擎还要额外维护删除标记与词典。

## 3. 中文分词与 ik

英文用空格天然分词，中文没有词边界，必须先分词。分词质量直接决定倒排表的召回：如果「倒排索引」被切成「倒」「排」「索」「引」，文档频率会被大量无意义单字稀释，查询也会命中一堆噪声。ik 是常用的中文分词器，提供 ik_smart 与 ik_max_word 两种粒度：前者偏向粗粒度、适合查询，后者细粒度、适合建索引。建全文索引时通常写 FULLTEXT INDEX ... WITH PARSER ik，让词项按词典切分后再进入倒排表。分词器还需要维护停用词表，把「的」「了」这类高频虚词排除，否则它们的文档频率接近文档总数，几乎没有区分度。

## 4. 与聚簇索引的区别

聚簇索引决定了数据行在磁盘上的物理顺序，InnoDB 的主键索引就是典型的聚簇索引：叶子节点直接存放整行数据，按主键顺序组织，因此主键范围查询很快，但二级索引需要回表。全文索引则是一种辅助索引，倒排表只保存词项与文档编号，查询命中后仍要按主键回表取原文。理解这一点很重要：聚簇索引优化的是「按主键找行」，倒排表优化的是「按词找文档」，两者解决的问题不同，不能互相替代。

## 5. 混合检索

只用倒排表时，查询词必须与文档用词一致，同义表达会漏召回；只用向量检索时，语义相近的片段能被召回，但精确术语与数字容易漂移。因此实际系统常把两路结果用 RRF 融合，并在返回片段时附带文档名与字符偏移，方便回溯原文。
