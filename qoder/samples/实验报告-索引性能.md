# 实验报告：B+ 树与 LSM 树的索引性能对比

## 1. 实验目的

本实验在同一台机器上比较 B+ 树与 LSM 树两类索引结构的读写性能，重点观察写放大、查询延迟与空间占用。测试数据为 2000 万条键值对，键为 16 字节随机串，值为 256 字节。B+ 树使用 InnoDB 的聚簇索引表，按主键随机插入；LSM 树使用基于 leveled compaction 的存储引擎，memtable 默认 64 MB。每组实验重复三次，取中位数，并在同一块 NVMe 盘上运行，避免缓存差异干扰结论。

## 2. 测试结果

| 指标 | B+ 树 | LSM 树 |
| --- | --- | --- |
| 随机写吞吐（ops/s） | 18500 | 42000 |
| 点查 P99（ms） | 0.8 | 2.6 |
| 范围扫描 P99（ms） | 1.4 | 3.1 |
| 磁盘写入量 / 逻辑写入量 | 1.06 | 3.8 |
| 索引占用空间（GB） | 42 | 57 |

可以看到，B+ 树的点查更稳定，因为一次查找只需从根走到叶，树高约为 4 层；写入时页面分裂会带来随机 I/O，写放大主要来自页分裂与日志。LSM 树把随机写先写入 memtable，再顺序刷盘，因此写入吞吐更高，但后台 compaction 需要反复重写 SSTable，写放大达到 3.8 倍。

## 3. 查询路径与聚簇索引

B+ 树实验中使用了聚簇索引，主键顺序与叶页顺序一致，范围扫描可以顺序读取叶页，代价接近 O(n/B)。如果改为二级索引，则需要回表，点查延迟会明显上升。LSM 的点查要先查 memtable，再按层级从新到旧查找，最坏情况要检查多个文件，因此 P99 高于 B+ 树。两类结构都依赖布隆过滤器跳过不可能包含目标键的文件，这也是 LSM 点查没有进一步退化的原因。

## 4. 全文检索与向量检索的补充实验

为了验证同一批数据上的检索能力，我们额外建立了全文索引与向量索引。全文索引使用 ik 分词器，对中文标题字段做分词后写入倒排表；向量索引则对摘要生成 384 维向量，用余弦距离做近似最近邻查询。测试发现，分词粒度会显著影响召回率：ik_smart 的召回略低但查询更快，ik_max_word 的词项更多、倒排表更大。向量检索在语义相似查询上明显优于关键词匹配，但对包含精确编号的查询不如倒排表稳定。因此线上系统采用混合检索，先分别取两路 top-k，再用 RRF 融合。

## 5. 结论

在写多读少的场景下，日志结构方案凭借顺序写获得更高吞吐，但以额外的合并开销和空间占用为代价；读多写少的场景则更适合原地更新的页式结构，尤其是需要范围扫描的主键查询。工程上应根据读写比例选择结构，并通过监控合并队列长度与点查尾延迟来动态调整参数。

## 附录：日志结构合并的写入代价

log-structured merge 家族的核心是把更新追加到新的 SSTable，而不是原地修改旧页。一次 compaction 需要读取多个层级文件，归并排序后写出新文件，再把旧文件标记删除。同一条记录可能在 L0 到 L3 之间被重写多次，写入量与逻辑写入量之比随层数与淘汰策略变化。我们在测试中把 compaction 线程数从 2 调到 8，后台写入量上升了约 18%，但前台尾延迟下降了 35%，说明合并策略需要在吞吐与延迟之间折中。空间回收滞后，旧版本要等到 compaction 之后才能释放，因此磁盘占用通常高于原地更新的结构。
