# CI 范围选择

持续集成通过 `.github/ci-paths.toml` 选择任务组，再为选中的任务分配 runner。各工作流使用自己的文件名调用 `ci-changes.yml`。文档变更选择网站与文档契约检查；独立宿主插件变更选择现有 Python 回归与对应宿主检查。无关的升级、worker 可观测性、安装角色、Desktop 和诊断矩阵会跳过。

无关变更仍可能出现轻量范围检测、Main 质量检查、许可证检查和升级结果门禁。升级矩阵跳过时，门禁明确表示本次不需要该验收，不代表升级已经通过。选中的矩阵必须成功；失败、取消或意外跳过不能通过门禁。发布仍直接调用安装包升级验收工作流，不通过路径选择绕过验收。

## 比较基线

- PR 比较 merge-base 到整个 PR head 的累计变化，覆盖全部提交，排除基准分支上的无关变更。
- push 比较同一工作流、同一分支上成功祖先提交到当前提交的变化。选择器通过只读 Actions API 查询最近最多 100 次成功的 push 运行，并检查祖先关系，拒绝采用重写历史中的不相关提交。取消或失败的运行不能作为基线，其尚未验证的变更会留在下一次比较中。
- 历史缺失、API 无法访问、元数据格式异常或差异获取失败时，选择全部任务组。因此，没有成功基线的新工作流会先执行完整验证。
- 定时和手动运行选择该工作流中的全部任务组。Desktop 安装包诊断、仅 recall 的 harness 等手动参数继续保留各自的限制。

选择器读取 Git 历史，不依赖 GitHub 截断后的路径过滤列表。关闭重命名检测，使移除和新增路径都参与选择。分支名按 API 查询参数编码，提交身份必须是完整十六进制 SHA。范围摘要记录比较区间、选择结果和回退原因。

## 维护归属规则

`[suites]` 将文件映射到单个任务组，`[shared.<name>]` 将共享输入映射到多个消费者。修改工作流会选择它自己的消费者，修改 composite action 会选择使用该 action 的工作流。选择配置、选择器、共享测试夹具和共享环境安装继续保留完整覆盖。未知路径在声明归属前也会选择全部任务组。

共享 Python Runtime、API 和根依赖变更仍保守覆盖运行时消费者、后端与升级验收、worker 可观测性及打包。历史 schema 捕获和 SeekDB 锁诊断具有独立输入，普通运行时代码变更不会启动这些开发工具。任务组选中后，原有 Python 版本和后端矩阵保持完整。

增加输入时，应包含所属目录之外的消费者。例如，Pi 变更也选择 ZCode 跨宿主验收；迁移相关测试变更应选择对应的真实后端验收。在 `tests/test_ci_changes.py` 增加选择回归。调整比较行为时，应验证移动、删除、差异不可用和 push 累计变更。

运行聚焦验证：

```sh
uv run pytest -q tests/test_ci_changes.py
uv run python scripts/check_workflow_actions.py .github/workflows .github/actions
```

本地范围测试使用真实 Git 历史和模拟 Actions 运行元数据，不执行 GitHub 调度器，也不代表原生宿主或后端验收。部署后应测量排队时间、runner 分钟和启动 job 数，再判断吞吐量是否改善。
