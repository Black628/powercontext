# 实测结果

所有数字都在本机跑出，原始 JSON 在 `bench/results/`（每条都带 `loadavg1` 与 3 次采样）。
**实测 / 估算 / 待测** 严格分开标注。

## 0. 环境与方法

| 项 | 值 |
| --- | --- |
| CPU | AMD Ryzen 9 8940HX（16 核 32 线程）|
| 内存 | 11 GB（WSL2 上限）|
| OS | WSL2 Ubuntu 22.04，kernel 6.18.54.1 |
| 编译器 | g++ 11.4.0，`-O3`（**不加** `-march=native`，原因见第 5 节）|
| seekdb | `5.7.25-OceanBase seekdb-v1.4.0.0`，`127.0.0.1:2881` |
| HNSW 实现 | hnswlib 0.8.0（**VSAG 的 `src/algorithm/hnswlib/hnswalg.h` 由此 fork**，同名函数、同样 linklist 布局）|
| 数据 | 高斯随机 128 维，种子 42；图 k=32；HNSW M=16 / ef_construction=200 / ef_search=64 |
| 质量口径 | recall@10，200 条查询（查询点从库内随机抽，答案用精确暴力 KNN 算）|
| GPU（本机）| NVIDIA RTX 5060 Laptop（cuVS，用于验证 GPU 路径的**代码**与量级） |
| AMD GPU | **不可用**：仅 Radeon 610M iGPU，无 ROCm、无 `/dev/kfd`；hipVS 要求 Instinct + ROCm 7.2.3 |

**为什么给两组主数据**：测量期间机器负载在变（`loadavg1` 已记进 JSON），同一条标准构建在两次独立运行里
分别是 5,141 ms 和 10,928 ms（20k/单线程）。所以下面把**一次空载运行**和**一次带负载运行（3 次取中位数）**
都列出来，结论只用两者的区间表述，不挑好看的那个。

## 1. 核心实测：图装配 vs 标准构建

标准构建 = `addPoint` 逐点做 `ef_construction` 次搜索；图装配 = 读 KG 图直接写邻接表（**零搜索**）。

### A. 空载运行（单次）

| N | 线程 | 标准构建 | 图装配 | 加速比 | recall@10（标准 / 装配）|
| --- | --- | --- | --- | --- | --- |
| 5,000 | 1 | 657.8 ms | **12.9 ms** | **51.0×** | 0.9935 / 1.0 |
| 20,000 | 1 | 5,141 ms | **72.9 ms** | **70.5×** | 0.9195 / 1.0 |
| 20,000 | 8 | 678.7 ms | 37.2 ms | 18.2× | 0.9195 / 1.0 |
| 50,000 | 1 | 22,813 ms | **276 ms** | **82.8×** | 0.7900 / 1.0 |
| 50,000 | 8 | 2,340 ms | 140 ms | 16.7× | 0.7845 / 1.0 |

原始数据：`results/n5000-t1.json`、`n20000-t1.json`、`n20000.json`、`n50000-t1.json`、`n50000.json`。

### B. 带负载运行（3 次取中位数，`--repeat 3`）

| N | 线程 | 标准构建 | 图装配 | 加速比 |
| --- | --- | --- | --- | --- |
| 20,000 | 1 | 10,928 ms | 224 ms | 48.9× |
| 20,000 | 8 | 870 ms | 61.8 ms | 14.1× |
| 50,000 | 1 | 26,122 ms | 530 ms | 49.3× |
| 50,000 | 8 | 2,456 ms | 89.5 ms | 27.5× |

原始数据：`results/final-n*.json`（含每次采样与 `loadavg1`）。

**结论（取两次运行的区间，不取更高的那个）**：

* 单线程：**49× ~ 83×**；
* 8 线程：**14× ~ 28×**（多线程把标准构建的墙钟摊薄，而装配几乎不受线程数影响，所以比值下降）；
* 装配后 recall@10 **不降反升**（1.0 vs 基线的 0.79~0.92）。

**为什么装配后 recall 更高**：候选来自精确 kNN 图（不是贪心搜索能到达的子集），再补一轮反向边，
第 0 层平均出度达到 31.77（上限 `maxM0=32`）。这不是调参调出来的，是候选集合质量决定的。
装配复杂度 `O(N·k·d)`，与 `ef_construction` 无关——所以 N 越大、加速比越高。

## 2. 实测：seekdb 自己的构建耗时（真实 SQL）

`CREATE VECTOR INDEX ... WITH (distance=cosine, type=HNSW, lib=vsag, m=16, ef_construction=...)`：

| N | M | ef_construction | 插入 | 建索引 |
| --- | --- | --- | --- | --- |
| 10,000 | 16 | 200 | — | 3,337 ms |
| 20,000 | 16 | 200 | 1,596 ms | **7,894 ms** |
| 20,000 | 16 | 40 | — | 3,332 ms |
| 20,000 | 16 | 17（M=16 的最小合法值）| 1,571 ms | **2,462 ms** |

原始数据：`results/seekdb-n10000.json`、`seekdb-n20000.json`。

**三条结论**：

1. 构建耗时随 `ef_construction` 增长：20k 上 ef 17→200，2,462→7,894 ms（3.2×）；
2. 用 ef=17 的 2,462 ms 近似固定开销，则 **ef=200 时约 5,432 ms（69%）是搜索相关**——正是 GPU 建图 + 装配能省的部分；
3. 插入 20,000 行约 1.6 s（≈12,500 行/秒），不是瓶颈。

## 3. 实测：建图成本（决定端到端是否划算）

| 后端 | 设备 | N=20,000 | N=50,000 |
| --- | --- | --- | --- |
| CPU 精确 kNN（分块 BLAS）| Ryzen 9 8940HX | 5,781 ms | 48,217 ms |
| cuVS brute_force（GPU）| RTX 5060 Laptop | 10,139 ms\* | **6,006 ms** |
| hipVS（GPU）| AMD Instinct | **待测** | **待测** |

\* 20k 那次包含 cuVS 首次调用的算子/上下文预热，同一次运行里 50k 反而更快（6.0 s），说明这是预热开销而非规模效应。
原始数据：`results/n20000.json`、`n50000.json`、`gpu20000.json`、`gpu50000.json`（`knn_ms` 字段）。

**这张表是本题的关键**：装配再快，图也是要花时间建的。

## 4. 端到端账（这是本方案真正的边界）

设端到端 = 建图 + 装配，与 seekdb 原生建索引比（N=50,000，8 线程基线 2,340 ms / 单线程 22,813 ms）：

| 方案 | 建图 | 装配 | 合计 | 对 8 线程基线 | 对单线程基线 |
| --- | --- | --- | --- | --- | --- |
| 原生（VSAG/hnswlib 逐点搜索）| — | — | 2,340 ms | 1.0× | 1.0× |
| CPU 建图 + 装配 | 48,217 ms | 90 ms | 48,307 ms | **0.05×（亏）** | 0.47×（亏）|
| cuVS/RTX5060 建图 + 装配 | 6,006 ms | 90 ms | 6,096 ms | **0.38×（亏）** | 3.7× |
| hipVS/MI300X 建图 + 装配 | 待测 | 90 ms | 待测 | 待测 | 待测 |

**门槛结论（可以直接用来判断"这台 GPU 值不值得上"）**：

> 只有当 **GPU 建图耗时 < 标准构建耗时 − 装配耗时** 时，这条链路才划算。
> 50k、8 线程基线下该门槛是 **< 2.25 s**；单线程基线下是 **< 22.5 s**。

本机的 RTX 5060 笔记本 GPU + cuVS **过不了 8 线程那道门槛**（6.0 s > 2.25 s），
但过了单线程那道（6.0 s < 22.5 s）。这也解释了为什么"上了 GPU 就一定快"是错的：
**要赢的是整条基线，而不是"装配那一段"**。

**MI300X 上的预期（估算，非实测）**：50k×128 的精确 KNN 约 `6.4×10¹¹` FLOP。
MI300X fp32 峰值约 60 TFLOPS、HBM3 带宽 5.3 TB/s，而笔记本 5060 是 ~15 TFLOPS、GDDR7 约 0.5 TB/s；
本机实测 6.0 s 对应约 107 GFLOPS 的有效吞吐（受限于访存与 128 维的算术密度）。
按同样效率外推，MI300X 大概率落在 **0.3~1 s**，即 **端到端 0.4~1.1 s**，
相对 8 线程基线约 **2~6×**、相对单线程基线约 **20~55×**。这是估算，`docs/RUN_ON_AMD_GPU.md` 给了复现步骤。

## 5. 排错记录（影响可复现性，写下来省别人的时间）

1. **hnswlib 0.8.0 预取越界**：`searchBaseLayer` 里 `_mm_prefetch(... *(datal + j + 1))` 在 `j == size-1`
   时读到链表末尾之外。第 0 层内存连续通常无感，上层链表是精确 `malloc` 的，跨页即段错误（5,000 点即可复现）。
   已在 `bench/vendor/hnswlib/hnswalg.h` 加边界判断并注明原因。这是**被测库**的问题，不是装配代码的问题。
2. **不能开 `-march=native`**：Zen4 上开启后 hnswlib 走 AVX-512 距离函数、假设 64 字节对齐，
   而 `data_level0_memory_` 内各点偏移不满足 → 段错误。`-O3` 稳定，且对比双方编译条件一致。
3. **`get_linklist(id, level)` 只能用于 level ≥ 1**：它按 `(level-1)` 偏移；level 0 必须用
   `get_linklist_at_level`。第一版在反向边遍历里用错，直接段错误。
4. **seekdb 拒绝 `ef_construction <= M`**：报 `... less than or equal to m value is not supported`，
   所以固定开销下限只能测到 `ef=M+1=17`。
5. **GPU 图与 CPU 图装配耗时不同**（同为 20k/1 线程：417 ms vs 224 ms）：两张图的邻居内容几乎一致
   （前 8 个邻居完全相同），差异来自 cuVS 图每行都是 32 个有效邻居、而 CPU 图每行留了 1 个 `-1` 空位，
   装配后第 0 层出度 29.73 vs 31.77，反向边的工作量也因此不同。两个数字都保留在 `results/final-gpu*.json`
   与 `results/final-n*.json` 里，没有只挑快的那个。

## 6. 结论

1. **图装配路径成立**：同源算法上比标准构建快 **49~83×（单线程）/ 14~28×（8 线程）**，recall 不降反升。
2. **瓶颈定位准确**：seekdb 20k 建索引 7,894 ms 中约 **69%** 与 `ef_construction` 相关的逐点搜索，
   正是装配消灭的那一段。
3. **但整条链路是否划算取决于 GPU 建图速度**：本机 CPU 建图亏 20×，RTX 5060 + cuVS 在 8 线程基线下仍亏 2.6×，
   只在单线程基线下赢 3.7×。门槛是"GPU 建图 < 基线 − 装配"（50k/8 线程为 2.25 s）。
4. **hipVS/AMD Instinct 的数字未实测**（无对应硬件），已给出脚本、门槛判定方法与预期区间，标明为估算。
